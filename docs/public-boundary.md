# Public boundary

## Safe to publish

- product purpose;
- high-level architecture;
- capability summaries;
- safety principles;
- roadmap state;
- fictional examples;
- public-safe diagrams;
- deliberately prepared screenshots.

## Keep private

- private source code;
- real machine reports;
- usernames, hostnames and environment identities;
- IP addresses, gateways and network topology from real systems;
- hardware serials and device identifiers;
- credentials, API keys, tokens and local runtime secrets;
- operational logs;
- quarantine, backup and restoration artifacts;
- local filesystem paths that are not necessary to explain the product;
- private deployment configuration;
- internal continuity checkpoints and pointers.

## Stale documentation rule

Historical source documents may still contain superseded synchronization descriptions. Public material follows the current source state and current ecosystem architecture, not stale private-GitHub assumptions.

## Principle

When evidence comes from a real diagnostic run, prefer recreating the example with fictional values instead of masking real operational data.
